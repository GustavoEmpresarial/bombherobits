## Fixes made

- Serialize smith and porter purchases using a database row lock; recheck ownership/prerequisites and debit gold conditionally inside the transaction.
- Atomically claim referral rewards so concurrent requests cannot award cards twice.
- Compare and update chest balance atomically to prevent duplicate reward credit.
- Reconnect the dungeon WebSocket after disconnection and show connection state.
- Persist and validate sound/volume preferences across navigation and reload.
- Preserve shared invite codes through wallet login and prefill the invite form.
- Allow the HTTP/WebSocket stamina integration test to target a configured test API rather than a hardcoded port.
- Correct a countdown accessibility-label typo and singular referral copy.

The new regression tests reproduced duplicate smith, porter and referral results before the fixes, then passed afterward. They also verify single charges, single referral rewards, insufficient balances and purchase prerequisites.

- Phantom/Solflare/Backpack extension signing and the original missing-keyring error could not be exercised inside the available browser. The real server signature flow was checked with a disposable Ed25519 wallet; this does not substitute for an extension end-to-end test.
- Fusion and Market are intentionally Coming Soon; trading through their API was not part of this playtest.
- Desktop browser verification used 1280×720; this was not a physical mobile-device test.

## Reproduce integration checks

Create/migrate a disposable PostgreSQL database and start an API connected to it. Set both DATABASE_URL and HEROBITS_TEST_API_URL to that isolated environment, then run:

```sh
HEROBITS_TEST_DATABASE=1 pnpm --filter @herobits/api test:integration
pnpm --filter @herobits/api test
pnpm --filter @herobits/api build
pnpm --filter @herobits/web build
```

Never point only one of the database/API settings at the disposable environment. QA credentials, auth bootstrap files and tokens must not be checked in or shipped in public/dist assets.

## Summon confirmation and interactive card reveal

Browser UI checks used the actual SummonProvider and SummonPage with isolated, in-browser API/auth fixtures. No player balance or production database was changed, and no Solana transaction was submitted. The current summon endpoint purchases with game balance and returns no blockchain signature, so the confirmation dialog explicitly waits for server confirmation.

Verified packs of 1, 5, 10 and 15 cards; automatic opening after purchase; one-card flip followed by reveal-all for the remaining four; one reveal request for a complete pack; collection delivery only after all cards have turned; and reopening a saved 15-card pack. The 15-card grid scrolls while its footer stays visible. Inspected the 375px layout and corrected card artwork clipping.

Injected a failed purchase, reveal and claim. Retrying purchase opened the expected ten-card pack; failed reveal left the card closed, then succeeded without another purchase; failed claim kept its revealed card, then succeeded and removed the pending pack. Keyboard focus is contained in the dialogs. Reduced-motion CSS disables looping/flip effects. Summon requests now time out after 30 seconds instead of leaving the confirmation blocked indefinitely.

### Follow-up: confirmation timing and claimed-pack resurrection

Confirmation presentation now lasts at least 2.6 seconds for normal motion, including a real confirmed state, with a minimum 700ms success beat after slower requests. Reduced-motion mode skips the presentation delay. Added four regression tests for timing, refresh ordering, a response captured before collection, and filtering claimed packs without hiding unfinished ones (58 tests pass).

The actual provider was exercised with a 20ms purchase fixture and an intentionally delayed pending-pack response captured before claim. After collection and delivery of the obsolete response, the browser showed zero pending packs; closing the popup left no pending section or claim button. Background refreshes also kept the list empty. No live account or database changes were used.
